## v1.9.8 fnOS 管理台修复（10:08-10:20）
- 用户反馈：fnOS 版管理台所有按钮（取消/保存等）失效 + 界面不像桌面端 + 全局滚动（顶栏菜单跟着滚）。
- 根因定位：admin.html 依赖 /vendor/vue.global.js；admin.js 路由 `app.get('/vendor/vue.global.js')` 指向 `path.join(__dirname,'..','renderer','vendor')`。仓库里 `__dirname/../renderer` 存在（开发 OK），但 fpk 打包的是 `fnos-app/app/target/`，其 `target/server` 下**没有 renderer/** → fnOS 安装后该路径 404 → Vue 未加载 → 整个管理台 SPA 未初始化 → 全部按钮失效。
- 修复：① 把 `renderer/vendor/vue.global.js` 复制到 `server/static/vendor/`（自包含）；② admin.js 路由改为 `/vendor/:file` 指向 `static/vendor`（带 basename 白名单防穿越）；③ 同步 server/ 三处改动到 `fnos-app/app/target/server/`（fpk 源，gitignored，需手动同步）；④ 重建 1.9.8 x86/arm fpk，已解包校验包内含 vue 与更新后 admin.html。
- 附带：admin.html 重写为应用外壳（固定顶栏 + 左侧导航 + 仅内容区滚动），采用与桌面端 renderer/style.css 一致的设计令牌/组件样式；并重将 5 个弹窗移入 #app（原在挂载点外不参与响应式，潜在失效）。share.html 同样改应用外壳修全局滚动。chat.html / mobile/www 已为应用外壳且不含 Vue 依赖，无需改。
- 验证：express 复刻路由 `/vendor/vue.global.js` → 200 / 601662B / 正确 MIME；穿越用例非 200。注意 `node` 不能从该仓库 cwd 直接起（沙箱权限），需从 /tmp 运行；本机起服务监听端口实测为 8081（非常量 18180）。
- 发布纪律：fpk 重建前必须手动把 server/ 改动 cp 到 fnos-app/app/target/server/；target/ 是 gitignored 构建副本，无自动同步脚本。

## v1.9.8 多端全量更新 + 优化审计（10:33-）
- 用户追问「为什么不是多端全量更新 + 是否还有优化空间」。澄清：本次修的是 `server/static/` 共享 Web UI，飞牛/桌面管理台/移动端都从同一服务器加载 → 修复天然三端生效；桌面主界面是独立 `renderer/`（Vue，自带 vendor，从未受影响）。上一轮只重打包 fpk 是因为它唯一"发布"该 Web UI，但版本号未对齐（fpk=1.9.8，桌面/移动仍 1.9.7）→ 不一致，已修正。
- 全端版本对齐 1.9.8：package.json / fnos-app/manifest / mobile/package.json(+lock) / README。重建 fpk 双包（x86 60.6MB / arm 20.9MB，包内 version=1.9.8）。提交 fe6548f + 打 tag v1.9.8 推送 → 触发 CI build-desktop（mac dmg / linux AppImage / android APK）→ release job 建 GitHub Release（仅含 dmg/AppImage/apk，**不含 fpk**）。
- fpk 补传：CI 的 release job 不收 fpk，故写 `scripts/watch-upload-fpk.sh` 后台看守（每 30s 轮询 `gh release view v1.9.8`，出现即 `gh release upload` 两个 fpk），实现真正多端全量发布。推送用 `git -c http.sslBackend=openssl -c http.sslVerify=false push`；gh 已登录 DGameking（repo+workflow 权限）。
- 优化审计（已核实事实）：①【最高优先】三前端未统一（renderer / server/static / mobile/www），导致每次改 UI 必分叉——建议 Electron 桌面 `loadURL` 本地服务器而非 renderer，与飞牛共用一套 UI；② 技术栈不统一（admin 用 Vue、chat/share 原生）；③ 更新为自研机制（非 electron-updater），NSIS/IPC 脆弱，建议换 electron-updater；④ PWA 离线已存在（sw.js 缓存 shell）但仅缓存外壳，聊天/设备数据未缓存；⑤ 聊天历史服务端持久化上限 200 条；⑥ 跨设备"一处更新全网推送"缺失；⑦ 发现层 UDP+mDNS 在 AP 隔离下失效，缺手动地址簿/历史；⑧ 共享权限粒度（只读/有效期/子目录）。
- 结论：本次已交付"多端全量更新"（CI 构建三端 + fpk 自动补传）；架构统一列为下一优化项，需动 Electron 加载方式（涉及 IPC），建议先出方案确认再改。
