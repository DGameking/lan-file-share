## 二、v1.10.0 投送协议升级（对标 LocalSend）

### 2.1 交付内容

| 功能 | 说明 |
|---|---|
| 三段式投送会话 | `prepare / session / decision` 协议：接收端关闭"自动接收"时，发送方先发文件清单，对端弹窗确认后才传输（对标 LocalSend 元数据先行审批，90s 会话 TTL） |
| sha256 完整性校验 | 小文件投送与分块合并均校验，不符拒收（HTTP 422）并清理残留；另加大小偏差校验 |
| 投送 PIN | 接收端可在「设置→投送 PIN」设置；发送端填写后自动携带，防误投/未授权投送 |
| mtime 还原 | 投送文件保留原始修改时间 |
| 组播发现 | UDP 心跳升级为「广播 + 组播 224.0.0.167」双发（LocalSend 同款选段，Android 兼容），提升跨路由/AP 隔离可达性 |
| 开放协议 v1 | `docs/protocol.md`：发现/投送/错误码/兼容性/路线图，第三方可实现互通 |

### 2.2 排查中修掉的真 Bug（旧版潜伏）

1. **文本投送永久挂死**：全局 `express.json` 中间件已预解析 body，drop 内手工 `req.on('data')` 读流永远等不到数据——旧版"剪贴板投送"功能实际已损坏，本轮改为直接用 `req.body` 修复。
2. **PIN 误判**：`String(undefined)` 返回字符串 `"undefined"`（真值），导致未填 PIN 被误报 `bad_pin`。
3. **自动接受漏写会话表**：prepare 自动接受分支返回 sessionId 但未写入 sessions Map，后续投送 404 `session_not_found`。

### 2.3 涉及文件

`server/drop.js`（协议核心）、`shared/constants.js`（组播常量）、`discovery/udp-broadcast.js`（双发）、`renderer/js/app.js`（审批等待轮询/确认弹窗/PIN 设置项）、`test/drop-e2e.js`（新增 13 项）、`docs/protocol.md`（新增）。

## 三、跨网段可行性验证（同光猫双路由器不同网段）

### 3.1 PoC 实测（`scripts/cross-subnet-probe.js`，已入库）

| 路线 | 方案 | 实测结果 |
|---|---|---|
| R1 | 跨网段定向探测（102 个候选网段网关 + 8080/9527 端口） | ❌ 全部不可达（出站跨网段被隔离，或当前仅 192.168.10.x 一个网段在用） |
| R2 | 邻层网关发现 | ⚠️ 依赖 R1 |
| R3 | UPnP 自动端口映射（SSDP 检测） | ⚠️ 路由器未开启 UPnP，当前不可用；开启后可用 `nat-api` 做直连增强 |
| **R4** | **光猫层会合点 + 中继** | ✅ **强烈可行，已实装为 v1.11.0** |

**核心洞察**：NAT 只拦"入站"，不拦"出站发起的会话"。NAS（fpk 服务端）挂在光猫 LAN 层，各网段设备**出站连 NAS 必然可达**；Hub 聚合跨网段设备表，传输数据经 NAS 暂存中继，完全绕开 NAT 穿透。

> 探测器本身修正了一个坑：本机多块 192.168.x 虚拟网卡导致候选网段被误过滤，改为按三段网段粒度比较后结论才可信。

## 四、v1.11.0 跨网段会合点

### 4.1 交付内容

| 模块 | 说明 |
|---|---|
| Hub 中心端 `server/hub.js` | 跑在光猫层 NAS/fpk：设备注册表聚合（30s 保活）、中继文件暂存转发（≤2GB/文件，**一次性拉取取后即删**，24h TTL） |
| 会合点客户端 `discovery/rendezvous.js` | 5 秒出站轮询注册 → 跨网段对端自动注入设备表（标记 relay）→ 中继文件拉取（sha256 校验 + mtime 还原 + 收件通知） |
| 桌面端 | 「设置→跨网段会合点」填 NAS 地址即可；中继设备投送自动走 Hub 路由（整文件 + 剪贴板） |
| 测试 | `test/hub-e2e.js` 三引擎本机模拟（Hub + A 网段 + B 网段）8/8 通过 |

### 4.2 实装中的关键修正

1. 引擎端口字段是 `this.httpPort` 而非 `this.port`（客户端注册曾报错）。
2. `deviceManager.upsert` 每次重建对象，relay/relay_hub 标记必须在 upsert 合并时保留，否则 UI 永远收不到中继设备。
3. 三引擎同机 e2e 时 UDP 广播会同时注入设备表，断言需轮询等待相位对齐（非产品 bug，测试时序问题）。

## 六、部署指南（用户家：光猫 + 双路由器拓扑）

1. **NAS（光猫层）**：安装 `LanFileShare-1.11.0-fnos-x86.fpk`——天然处于会合点位置，即装即 Hub。
2. **两台路由器下各设备**：装 1.11.0 客户端，「设置 → 跨网段会合点」填 NAS 的 `IP:端口`。
3. 几秒内设备表互见（带中继标记），拖拽投送即走：A →（出站）→ NAS 暂存 → B（出站拉取）。
4. 可选增强：路由器开启 UPnP 后，后续版本可做免中继满速直传（R3 路线已预留）。

## 七、已知限制与下一步

**已知限制**
- 中继走整文件（≤2GB）；分块断点续传暂不经过中继。
- 投送审批弹窗流程（prepare/decision）不跨中继，中继投送直接落「收到的投送」。
- 中继速率受 NAS 所在链路限制（光猫层通常千兆）。
- 大文件（>64MB）分块路径暂无 sha256（浏览器端无法流式摘要），以大小校验兜底。
- 真机飞牛端与真实双路由拓扑的端到端表现待装后反馈。

**下一步路线（已写入 `docs/protocol.md`）**
- v1.1：deviceType/友好别名字段、逐 IP 降级发现、上传前缩略图预览。
- v1.2：UPnP 直连增强（路由器开 UPnP 后免中继满速直传）、与 LocalSend 协议互通网关。
- 待用户复测：在真实双路由拓扑各放一台设备跑 `node scripts/cross-subnet-probe.js`，确认 R1/R2 真实形态。

## 八、结论

本轮以「调研 → 落地 → 验证 → 再落地」闭环交付：LocalSend 的协议精华（会话审批/sha256/PIN/组播）已全部吸收进 v1.10.0；spacedesk 的工程模式（角色收敛、降级自愈）持续沿用；针对用户提出的"同光猫双路由器不同网段互通"诉求，经 PoC 实测否掉直连/UPnP 主路线，采用**光猫层会合点 + 中继**方案在 v1.11.0 全量交付。两版发布资产齐整、测试全绿、协议文档同步，平台具备与第三方实现互通的开放基础。
