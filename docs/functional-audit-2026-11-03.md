# 功能性审校报告 · 缺失盘点与完善路线

**审校对象**：lan-file-share v1.11.0（全模块源码走读 + 关键路径实证）
**审校日期**：2026-11-03
**审校方法**：源码走读（server 5146 行核心 + renderer/main/mobile）、与 LocalSend/spacedesk 基准对照、真实使用场景推演（光猫双路由拓扑 / NAS 常驻 / 手机访客）

---

## 一、总体评价

功能面已覆盖「共享 / 会话 / 投送 / 挂载 / 跨网段」五大主干，工程底子扎实（协议文档、e2e 测试、全端发布流水线齐全）。但按「能长期用的产品」标准衡量，存在 **3 个结构性短板**：

1. **安全基线落后于功能增速**——新功能全走默认 HTTP，敏感字段明文；
2. **接收侧体验断层**——收到的文件"看得见管不着"（历史易失、无配额、无管理）；
3. **状态不可视**——会合点/桥/发现均为"黑盒"，出问题用户无从下手。

---

## 二、逐项审校发现（按严重度）

### 🔴 P0 · 安全与数据（建议本版热修）

| # | 发现 | 证据 | 影响 |
|---|---|---|---|
| S1 | **投送/中继路由未挂 IP 过滤与限流中间件** | `server/index.js` 仅全局挂 express.json + 日志；`middleware/ip-filter`、`rate-limit` 存在但未覆盖 drop/hub 路由；drop.js 内仅 checkPin | 任意同网段设备可无限投送打满 `received` 磁盘；被拉黑 IP 仍可投送 |
| S2 | **PIN/凭据明文 URL 传输** | drop.js 以 `?pin=123456` query 传 PIN；全链路默认 HTTP | PIN、共享密码（WebDAV Basic）、管理令牌可被同网段嗅探。**至少应改放请求头/body** |
| S3 | **received 目录无配额、无清理、管理台不可见** | recv-util.js 直接落盘，无总量控制 | NAS 场景磁盘可被投送写满 |
| S4 | **接收历史不持久化** | renderer `received = ref([])` 内存态，>30 条丢弃，重启清零，无 localStorage/DB 落盘 | 关掉窗口历史全丢，LocalSend 有完整历史 |
| S5 | **README 承诺的 SHA256SUMS.txt 实际未生成** | v1.11.0 Release 9 项资产中无此文件 | 与 README"每个 Release 附带 SHA256SUMS.txt"矛盾，自证完整性的承诺落空 |

### 🟡 P1 · 体验断层

| # | 发现 | 证据 | 影响 |
|---|---|---|---|
| E1 | **WebRTC 屏幕共享/通话依赖 HTTPS，但 HTTPS 默认关** | chat.js WebRTC 信令 + README"需在设置中开启 HTTPS" | 默认装完即"功能存在但用不了"，用户视角是坏的 |
| E2 | **会合点状态黑盒** | rendezvous.js 注册失败仅静默重试；renderer 无连接状态/最后同步时间/失败提示 | 填错 Hub 地址用户毫无感知，以为"打通了" |
| E3 | **中继三大限制未补** | ≤2GB 整文件、分块续传不走中继、审批流程不跨中继 | 跨网段传大文件断网即重头再来 |
| E4 | **>64MB 分块路径无 sha256** | 浏览器端无法流式摘要，仅大小校验 | 大文件静默损坏无法发现 |
| E5 | **聊天历史固定 200 条无分页** | chat.js `listChatMessages(200)` | 老消息不可回溯 |
| E6 | **收件项不可管理** | received 列表只有"打开文件夹" | 不能单文件打开/删除/另存/重发 |

### 🟢 P2 · 补全项（对齐竞品/场景）

| # | 发现 | 说明 |
|---|---|---|
| F1 | Android APK 仅 96 行连接页壳 | 无系统分享菜单接入、无后台接收通知、无自动发现（手填地址） |
| F2 | deviceType/友好别名/设备图标缺失 | 协议 v1.1 已列，未实装 |
| F3 | 逐 IP 降级发现缺失 | 组播+广播都失效的网络（AP 隔离）只剩手动 IP |
| F4 | 默认密码 admin 有横幅不强制改 | 无强度校验、无"登录即提醒修改"拦截 |
| F5 | 访客上传（浏览器→共享方）无断点续传 | 只有下载 Range 和 drop 分块有 |
| F6 | 无传输队列暂停/取消 | 大文件传错只能等完或杀进程 |

## 三、功能缺失盘点（对照 LocalSend 与真实场景）

| 能力 | LocalSend | 本工具 | 差距定性 |
|---|---|---|---|
| 接收前预览（缩略图/首帧） | ✅ | ❌ | 缺失，审批弹窗只看文件名 |
| 传输历史持久化 | ✅ | ❌（内存 30 条） | **结构性缺失** |
| 单文件重传/取消 | ✅ | ❌ | 缺失 |
| 设备类型/别名 | ✅ | ❌ | 缺失（协议已规划） |
| 端到端加密默认开 | ✅（HTTPS 强制） | ❌（HTTP 默认） | **最大差距** |
| 跨网段 | ❌（官方不做） | ✅（会合点） | **反超项，应保持并宣传** |
| 会话/聊天 | ❌ | ✅ | 反超项 |
| 共享目录+磁盘挂载 | ❌ | ✅ | 反超项 |
| NAS 常驻中心 | ❌ | ✅（fpk/Hub） | 反超项 |

**结论**：本工具的差异化在"会话 + 挂载 + 跨网段 + NAS 中心"，这三项 LocalSend 都没有；差距集中在"传输安全默认值"和"接收侧管理"。完善策略应是**守住反超项、补齐安全与收件箱**，而不是盲目堆功能。

## 四、完善路线（可执行方案）

### v1.11.1 热修（半天~1 天，只修不加）
1. **S2**：PIN/凭据改 `X-LFS-PIN` 请求头传递（客户端+服务端同步改，保留 query 兼容一个版本）；
2. **S1**：drop/hub 路由挂 ip-filter + 简单令牌桶限流（如 10 文件/分钟、并发 3）；
3. **S3**：received 加配额上限（默认 10GB，可在设置改）+ 超限拒收提示；
4. **S4**：接收历史落 SQLite（新表 `drop_history`），UI 加载最近 200 条；
5. **S5**：CI/本机构建后生成 SHA256SUMS.txt 并 `gh release upload`，README 承诺兑现。

### v1.12 收件箱与可视（1~2 天）
6. **E6**：收件项单文件打开/删除/另存/重新投送；
7. **E2**：设置页会合点状态灯（已连接/最后同步时间/失败原因），复用 diagnostics 自检加"会合点连通性"一项；
8. **E1**：HTTPS 引导流——检测到用户点"屏幕共享/通话"而 HTTPS 未开时，弹窗一键开启+重启引导（自签证书生成已具备）；
9. **E3**：中继分块化（Hub 按 8MB 块暂存拼接，复用 drop 分块协议）+ 审批事件经 Hub 转发；
10. **E4**：分块路径补 sha256——按块计算分片哈希 + 合并后全量哈希（Node 侧流式计算无障碍，浏览器侧按块算分片）。

### v1.13 对齐 LocalSend（按需）
11. **F2/F3**：心跳补 deviceType/alias，设备页图标区分 PC/手机/NAS；逐 IP 降级发现；
12. **F1**：Android 原生化——`ACTION_SEND` intent-filter 接入系统分享菜单、前台服务接收通知、mDNS 自动发现；
13. **F5/F6**：访客上传断点续传 + 传输队列暂停/取消。

### v2 方向（立项评估）
- LocalSend 协议互通网关（映射到 `/api/localsend/v2/*`）；
- UPnP 直连增强（路由器开 UPnP 后免中继满速直传）；
- SFU 通话规模化、多语言。

---

## 五、结论

- **必须立即处理**：S1~S5（安全基线 + 历史持久化 + SHA256SUMS），其中 S2/S3 在局域网真实使用中是实际风险而非理论风险；
- **最伤体验的一处**：E2 会合点黑盒——这是你本次主推的卖点功能，填错地址无任何反馈，建议随 v1.12 优先解决；
- **差异化优势**（会话/挂载/跨网段/NAS 中心）应持续投入并写进门面宣传，不必追赶 LocalSend 的所有功能点。
